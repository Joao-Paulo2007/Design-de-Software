# ADR-0003: Correção de Problemas de Estruturação

## Status
[Proposto]

## Problema Analisado

Durante a análise de um código proposto para melhorias, foram identificados alguns problemas de estruturação que podem dificultar a manutenção e a evolução do sistema.
Os principais problemas encontrados foram acoplamento, baixa coesão, duplicação ou concentração de responsabilidades e uso excessivo de estruturas condicionais.

### 1. Baixa coesão e excesso de responsabilidades

**Nome do problema:** Baixa coesão e violação da responsabilidade única.
**Evidência:** A classe `LegacyShippingService` possui o método `process`, que realiza várias atividades diferentes: calcula o valor do frete, identifica a transportadora, envia uma notificação por e-mail e registra um log.
**Causa provável:** As diferentes funcionalidades foram concentradas em uma única classe durante a implementação, fazendo com que ela assumisse responsabilidades que poderiam pertencer a componentes separados.
**Impacto:** A manutenção fica mais difícil, pois uma alteração em uma funcionalidade pode exigir modificações em uma classe responsável por várias outras atividades. Isso também dificulta os testes, já que diferentes comportamentos precisam ser avaliados dentro do mesmo componente.
**Hipótese inicial de melhoria:** Separar as responsabilidades em métodos ou classes específicas, deixando cada componente responsável por uma função bem definida.

### 2. Acoplamento entre regras diferentes

**Nome do problema:** Acoplamento.
**Evidência:** O método `process` possui diretamente as regras relacionadas ao cálculo do frete, às transportadoras, às notificações e aos logs.
**Causa provável:** As funcionalidades foram implementadas diretamente dentro do fluxo principal do serviço, sem uma separação clara entre as diferentes partes do processo.
**Impacto:** Alterações em uma dessas funcionalidades podem afetar o funcionamento das demais. A inclusão de uma nova transportadora, por exemplo, exige alteração no mesmo método que também controla o cálculo do frete e as notificações.
**Hipótese inicial de melhoria:** Separar as responsabilidades em componentes independentes e fazer com que o serviço principal apenas coordene o processo.

### 3. Uso excessivo de estruturas condicionais

**Nome do problema:** Excesso de `if/else` e regras fixas espalhadas pelo código.
**Evidência:** O código utiliza estruturas condicionais para verificar os tipos de frete:
`ECONOMICO`, `EXPRESSO` e `PRIORITARIO`.

Também existem estruturas semelhantes para verificar as transportadoras `CORREIOS` e `RAPIDEX`.
**Causa provável:** As opções disponíveis foram implementadas diretamente por meio de comparações entre `String`.
**Impacto:** A adição de novos tipos de frete ou transportadoras exige alterações no método existente. Isso aumenta a possibilidade de erros e reduz a clareza do código.
**Hipótese inicial de melhoria:** Utilizar `Enum` para representar os tipos de frete e as transportadoras. Os valores fixos necessários para o cálculo do frete podem ficar associados ao próprio `Enum`.

### 4. Possível duplicação de lógica

**Nome do problema:** Duplicação ou dispersão de lógica.
**Evidência:** A identificação das opções de frete e transportadoras depende de várias comparações de `String` dentro do mesmo método. Caso novas funcionalidades sejam adicionadas utilizando as mesmas informações, essas verificações podem precisar ser repetidas em diferentes pontos do sistema.
**Causa provável:** As informações sobre os tipos de frete e transportadoras não estão centralizadas em uma estrutura própria.
**Impacto:** A repetição de regras aumenta o custo de manutenção e pode fazer com que diferentes partes do sistema apresentem comportamentos inconsistentes.
**Hipótese inicial de melhoria:** Centralizar as informações utilizando `Enum` e métodos específicos para cada responsabilidade.

O código analisado com as anotações de correções pode ser encontrado no arquivo [codigoComentado.java](codigoComentado.java).

## Decisão
Será realizada uma reorganização da estrutura do código, separando as diferentes responsabilidades em métodos e classes específicas.

As principais modificações serão:
- Dividir as responsabilidades da classe em métodos ou componentes específicos, de forma que cada um tenha uma função bem definida.
- Substituir os if/else utilizados para identificar os tipos de frete por um Enum, contendo os tipos disponíveis e os valores fixos necessários para o cálculo.
- Criar um método específico para realizar o cálculo do frete, utilizando os valores definidos pelo Enum.
- Utilizar um Enum para representar as transportadoras disponíveis, evitando erros relacionados à escrita dos nomes e facilitando futuras alterações.
- Separar o gerenciamento das notificações do processamento principal do frete.
- Separar o registro de logs das demais responsabilidades da classe.
- Manter o método principal responsável apenas por coordenar o processo de envio, delegando cada responsabilidade para o componente adequado.

Com essa estrutura, cada parte do código terá uma responsabilidade mais específica, facilitando a compreensão, manutenção e expansão do sistema.

## Alternativas Consideradas

### 1. Manter a estrutura atual

Manter todos os processos dentro da classe LegacyShippingService, realizando apenas pequenas alterações no código existente.
Essa alternativa seria a mais simples de implementar inicialmente, porém manteria os principais problemas encontrados, como a baixa coesão e a concentração de responsabilidades.

### 2. Utilizar apenas switch no lugar dos if/else

Outra possibilidade seria substituir as estruturas if/else por switch para identificar os tipos de frete e as transportadoras.
Apesar de melhorar parcialmente a organização do código, essa alternativa ainda manteria as informações dos diferentes tipos diretamente dentro da classe, além de não resolver o problema da concentração de responsabilidades.

### 3. Utilizar Enum e separar as responsabilidades

A alternativa escolhida consiste em utilizar Enum para representar os tipos de frete e transportadoras, além de separar as diferentes responsabilidades em métodos ou classes específicas.
Essa abordagem apresenta uma estrutura mais organizada e facilita futuras alterações, como a inclusão de novos tipos de frete, transportadoras ou formas de notificação.


## Consequências

### Vantagens
- Maior organização e legibilidade do código.
- Redução da quantidade de estruturas condicionais.
- Menor possibilidade de erros causados pela escrita incorreta dos tipos de frete ou transportadoras.
- Maior facilidade para adicionar novos tipos de frete ou transportadoras.
- Cada componente passa a possuir uma responsabilidade mais específica.
- Facilita a manutenção e os testes das funcionalidades individualmente.
- Reduz o acoplamento entre o cálculo do frete, as notificações, as transportadoras e os logs.
- Facilita futuras alterações sem a necessidade de modificar uma única classe responsável por várias funcionalidades.

### Desvantagens
- A implementação inicial será mais trabalhosa devido à necessidade de criar novos métodos, Enums e possivelmente novas classes.
- O projeto poderá possuir uma quantidade maior de arquivos e componentes.
- Para alterações simples, pode ser necessário acessar mais de uma classe.
- A separação das responsabilidades exige uma organização maior da estrutura do projeto.
